    微服务过渡合约¶

    从当前过渡到的目标架构和迁移规则 模块化整体到可独立部署的服务。本文档不 声称当前模块已经是服务。

    1. 决定¶

    该平台将发展成为包含多个可部署 Symfony 的 monorepo 应用。服务拥有其运行时、数据库模式、迁移、工作线程 队列、计划作业和部署工件。拆分成单独的 Git 存储库被明确推迟，直到服务边界和合同确定为止 稳定。

    第一个迁移阶段建立目标目录结构并 依赖治理。它不会移动每个当前的 src/* 模块或拆分 过早地建立数据库。

    2. 目标存储库结构¶

    apps/
  commerce/               # Transitional home for Catalog, Ordering, Pricing
  store/
  inventory/
  payment/
  wallet/
  identity/
  content/
packages/
  platform-kernel/        # Framework-only HTTP/CRUD/observability utilities
  integration-contracts/  # Versioned transport-neutral event schemas
  test-support/
contracts/
  integration/            # Manifest, schemas, and compatibility fixtures
  openapi/                # Published service API contracts
infrastructure/
  docker/
  local/
  gateway/
  rabbitmq/
docs/
tools/

    每个 apps/* 都是可独立构建的并包含自己的 composer.json、src/Kernel.php、config/、migrations/、public/、bin/、 tests/，以及 Docker 构建定义。根 Composer 工作区可以协调 本地开发，但不得隐藏未声明的运行时依赖项。

    3. 当前和目标边界¶

    目标环境 当前来源 初始位置
    平台内核 核心 共享图书馆，绝不是商业服务
    身份和访问 身份加微信登录适配器 稍后提取
    商业 贸易+促销 过渡服务；目录和订购稍后分开
    店铺运营 商店 → apps/store 提取；过渡期间的整体主机
    库存 库存 → apps/inventory 提取；过渡期间的整体主机；生产支持仍然受到安全检查表的阻碍
    付款 支付加微信支付适配器 持久支付生命周期事件存在后
    钱包/分类账 钱包 付款后合同是标量且持久的
    内容/媒体 普通+存储适配器 之后;首先从 CMS 中分离设置所有权

    Wechat 是提供者集成命名空间，而不是未来的有界上下文。其 登录功能属于身份适配器，其支付功能属于 在支付适配器后面。 Storage 是基础设施，而不是商业服务 默认。

    4. 服务边界规则¶

    在模块可以独立部署之前，应用以下规则：

    1. 一个服务拥有自己的数据库并且没有跨服务的 Doctrine 关联， 外键、存储库访问或事务。 2.持久的跨服务引用使用UUID或记录的不可变业务 键，绝不是其他服务的本地整数主键。
    2. 服务边界接受标量命令/查询并发出标量快照。 它从不公开 Doctrine 实体、存储库、EntityManagers、Symfony 请求/响应，或可变的进程内上下文。
    3. 状态更改集成事件被写入生产者的发件箱 本地交易。消费者使用持久的收件箱（或等效的消费事件 记录）由eventId键入。
    4. 每个消费者拥有自己的队列、重试策略、死信处理、worker 和 预定的工作。共享 Doctrine Messenger 队列不是服务边界。
    5. 共享包可以提供框架实用程序、模式和测试支持。 它们不得包含业务实体、存储库或特定于服务的 应用逻辑。
    6. 公共路由通过 API 网关或路由层保持稳定，同时 所有权在服务之间转移。

    5. 集成消息合约¶

    所有集成事件和命令都使用一个版本化信封：

    {
  "eventId": "uuid",
  "type": "store.order.accepted",
  "version": 1,
  "aggregateType": "store_order",
  "aggregateId": "uuid",
  "occurredAt": "2026-07-29T12:00:00+00:00",
  "correlationId": "uuid",
  "causationId": null,
  "payload": {}
}

    type 没有版本控制。经纪人主题派生为 type + ".v" + version；例如，store.order.accepted.v1。所有九个领域 规范 v1 信封中需要。 causationId 可以为空。

    schema 和manifest 归contracts/integration所有，而PHP 运营商 类位于 packages/integration-contracts 中，而不是生产者或消费者中 Symfony 命名空间。更改需要新的消息版本和兼容性 覆盖范围。

    事件是带有明显kind: "event"的过去时事实。请求如 inventory.reservation.requested.v1 和 inventory.reservation.release.requested.v1 是命令 kind: "command"，即使他们使用相同的信封。旧版信使 包装类位于 packages/legacy-messenger-compat 中并保持兼容性 输入，直到旧的本机 PHP 序列化队列行和失败消息已被处理 排干或迁移。

    5.1 运营商迁移命令¶

    必须在生产者更改运营商类型之前部署消费者。期间 兼容阶段，每个现有处理程序都接受其遗留的 App\*\Message 包装器和匹配的中立载体，然后委托给 相同的业务逻辑。制作者继续为每个主题仅发布一个载体； 双重发布是被禁止的，因为并非每个消费者行为都是收件箱幂等的。

    部署消费者后，发布者可以一次从主题切换一个主题 传统包装器到中立载体。回滚仅将该发布者更改回 遗留包装器。消费者和旧的包装类保持兼容性 打包直到 async 和 failed 队列不再包含旧的本机 PHP 序列化的消息。

    所有九个贸易、商店和库存主题现在都发布其匹配的中性主题 载体。本机 PHP 序列化程序暂时保留，因此载体对象是 仍然存储在现有的 Doctrine 队列中；该更改删除了应用程序模块 来自新生成的消息的 FQCN，无需更改传输。主题级 回滚仅将其发布者更改回匹配的旧包装器。消费者 和包装器将保留，直到历史 async 和 failed 队列记录完成 已被耗尽或迁移。

    存储目录所有权通过单独同步 store.directory.upserted.v1。存储更改将此事件写入同一事件中 交易，并且 Trade 维护 X-Store-Code 的本地只读投影 分辨率。在生产中将 Trade 切换到此投影之前，运行 app:store:outbox:backfill-directory 作为一次演练，然后使用 --apply 来 初始化现有商店的事件。

    5.2 发件箱元数据扩展¶

    每个生产者发件箱都存储可为空的 correlation_id 和 causation_id 列 在发布规范信封之前。在支持的 MySQL 8 运行时上 迁移明确请求ALGORITHM=INSTANT；它执行不 表范围更新并且不添加非空约束。新根 消息默认 correlationId 为其生成的 eventId 并使用 null causationId。发出后续消息的未来处理程序必须显式携带 入站 correlationId 并将入站 eventId 用作 causationId。

    当前的 Trade -> Store -> Inventory 链将此传播应用于每个 派生的发件箱消息。没有相关 ID 的旧信封仍然被接受； 它们的 eventId 成为兼容性相关根。这个后备是 临时兼容性行为，不能替代规范信封。

    在此扩展阶段，历史行在元数据为空的情况下仍然有效。后来， 单独的、可恢复的回填命令将按有限批次更新未发布的行 并报告进展情况。它必须在任何非空约束之前部署和观察 或考虑发布商切换。

    默认情况下，有意手动进行回填并进行空运行。运行每个服务 命令使用保守的生产批量大小，观察报告的计数和 数据库加载，然后重复直到试运行报告为零：

    php bin/console app:trade:outbox:backfill-correlation --limit=500
php bin/console app:trade:outbox:backfill-correlation --limit=500 --apply
php bin/console app:store:outbox:backfill-correlation --limit=500 --apply
php bin/console app:inventory:outbox:backfill-correlation --limit=500 --apply

    每个条件更新都会重新检查该行是否未发布且缺少 相关 ID。该命令既不更新已发布的行，也不更改 causation_id，因此可以在中断后安全地恢复并与 发件箱出版商。不得将其添加到调度程序中。

    6. 撤离顺序和门¶

    存储特定的依赖项库存和源移动门维护在 。

    首选顺序是：

    Store -> Inventory -> Payment -> Wallet

    商店和库存已使用 UUID/快照集成流程和发件箱/收件箱 模式。它们是候选服务，而不是自动生产就绪的服务。 库存必须保留其记录的功能标志和安全限制，直到 它的履行、到期、排序和并发保证是完整的。

    支付、钱包、身份、商务、促销、内容和提供商适配器 必须首先在整体内部解耦。所需工作的示例：

    • 用外部用户 UUID 替换共享 Identity\Entity\User 关联 本地投影/快照。
    • 将支付的同步 Doctrine 实体事件替换为支付发件箱 商务收件箱事件。
    • 取消 Trade 的直接钱包转账路径，转而采用支付边界。
    • 替换暴露Invoice或的支付网关和调整插件API Symfony HTTP 类型具有服务拥有的命令和结果契约。
    • 用标量报价请求替换促销的共享可变定价上下文 在考虑远程执行之前确定性结果。

    7. 第一阶段可交付成果¶

    仅当满足以下所有条件时才认为目录重组完成 即使在移动业务代码之前就存在：

    • 目标apps/、packages/、contracts/、infrastructure/和tools/所有权 模型被记录并反映在存储库工具中。
    • 架构检查拒绝禁止的跨服务导入和实体泄漏。
    • 现有的贸易、商店和库存事件共享第 5 节中的信封。
    • 一个服务模板定义了独立的Kernel、配置、迁移、队列、 工作人员、调度程序、Docker、测试、静态分析和 CI 所有权。
    • 传统的模块化整体测试套件仍然作为表征套件 直至相关服务提取完成。

    8. 非目标¶

    • 移动目录而不强制执行可部署边界。
    • 为每个当前模块创建空服务应用程序。
    • 将Core提取为网络服务。
    • 按文件名拆分历史迁移；混合遗留迁移仍然存在 重建整体，而提取的服务从经过验证的模式开始 基线和新的服务本地迁移历史。
