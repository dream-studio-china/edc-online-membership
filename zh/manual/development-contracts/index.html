    开发合同¶

    所有贡献者必须遵循的开发规则、约定和质量关卡。 源自 docs/design/system-architecture.md、docs/design/system-contracts.md、 和实际的代码库模式。

    1. 图层规则¶

    docs/design/system-architecture.md 1.1 节中的层依赖表：

    规则 来自 至 允许
    R1 控制器 服务 是
    R2 控制器 实体 是（仅键入提示/返回）
    R3 控制器 存储库 否 — 通过服务
    R4 控制器 实体管理器 否 — 通过服务
    R5 服务 存储库 是
    R6 服务 实体 是
    R7 服务 实体管理器 是
    R8 服务 其他服务 是（通过 DI）
    R9 实体 存储库 不
    R10 实体 服务 不
    R11 实体 实体管理器 不

    控制器不得： - 注入EntityManager - 调用beginTransaction()、commit()、rollback() - 直接调用存储库 - 使用$_GET、$_POST、$_REQUEST超全局变量 - 包含业务逻辑（委托给服务）

    服务必须： - 拥有所有业务逻辑、交易、验证 - 使用wrapInTransaction()进行多实体突变 - 返回实体或 DTO（绝不将原始数据库结果发送给控制器）

    2. 跨模块通信¶

    2.1 允许¶

    来自 至 机制
    任何业务模块 核心 DI（autowire 核心服务）
    业务模块A 业务模块B DI（自动装配B的服务接口）
    任何模块 身份 当前主要抽象或导出服务

    2.2 禁止¶

    图案 原因
    直接跨模块实体访问 使用显式模块 API 或标量引用/快照
    直接跨模块存储库访问 使用服务接口
    循环模块依赖 违反层架构
    核心导入业务模块 核心是基础

    2.3 跨界身份¶

    背景 标识符
    一个模块内的本地学说关系 允许使用整数 id
    公共 API 路由/响应 UUID
    跨模块边界的服务接口 UUID 或记录的不可变业务密钥
    集成事件聚合/源/关联 ID UUID
    未来服务数据库关系 仅 UUID/业务密钥；没有跨服FK

    3. 服务边界规则¶

    从docs/design/microservice-transition.md来看，提取前的7条规则：

    1. 服务拥有自己的数据库，没有跨服务的 Doctrine 关联、外键、 存储库访问或事务。
    2. 持久的跨服务引用使用 UUID 或记录的不可变业务密钥，永远不会 另一个服务的本地整数主键。
    3. 服务边界接受标量命令/查询并发出标量快照。它从来没有 公开 Doctrine 实体、存储库、EntityManager、Symfony 请求/响应，或 可变的进程内上下文。
    4. 状态改变的集成事件被写入生产者本地的发件箱 交易。消费者使用由 eventId 键控的耐用收件箱。
    5. 每个消费者拥有自己的队列、重试策略、死信处理、worker 和调度 工作机会。共享 Doctrine Messenger 队列不是服务边界。
    6. 共享包可以提供框架实用程序、模式和测试支持。他们绝不能 包含业务实体、存储库或特定于服务的应用程序逻辑。
    7. 当所有权转移时，公共路由通过 API 网关或路由层保持稳定 服务之间。

    提取前检查表： - [ ] 所有跨模块引用都使用 UUID 或不可变的业务密钥 - [ ] 没有共享的学说关联或跨模块 FK - [ ] 集成事件使用发件箱/收件箱模式 - [ ] 服务有自己的composer.json、Kernel.php、config/、migrations/、public/、 bin/、tests/、Docker 定义 - [ ] 架构检查 (deptrac) 通过，无需新的基线条目 - [ ] 旧测试套件保持绿色

    4. 命名空间约定¶

    层 命名空间
    核心框架 App\Core\*（在 packages/platform-kernel/src/ 中）
    模块控制器 App\{Module}\Controller\Manage\ 或 App\{Module}\Controller\App\
    模块实体 App\{Module}\Entity\
    模块存储库 App\{Module}\Repository\
    模块服务 App\{Module}\Service\
    模块异常 App\{Module}\Exception\
    模块事件监听器 App\{Module}\EventListener\
    模块命令 App\{Module}\Command\
    桥接适配器 App\Bridge\{Module}\
    整合合同 App\Contracts\Integration\

    路由命名：{scope}-{resource}-{action}（例如manage-categories-list， app-orders-create、system-router-list）。

    5. 文件命名¶

    规则 详情
    每个文件一个类 无一例外
    文件名=类名 CategoryService.php 包含 class CategoryService
    特征文件 与特质同名
    接口文件 与接口同名
    测试 {Class}Test.php
    PSR-4 自动装弹 目录镜像命名空间，区分大小写

    6. 类约定¶

    6.1 必需¶

    <?php
declare(strict_types=1);

namespace App\Common\Service;

use App\Common\Entity\Category;
use App\Core\Service\BaseService;

/** @extends BaseService<\App\Common\Entity\Category> */
class CategoryService extends BaseService implements CategoryServiceInterface
{
    public function __construct(/* ... */) { /* ... */ }
}
    • declare(strict_types=1) 位于每个 PHP 文件的顶部
    • final 如果适用（防止意外扩展）
    • readonly 用于尽可能构造函数注入的依赖项
    • #[ORM\*] 用于 Doctrine 映射的 PHP 属性（不是注释）
    • #[OA\*] OpenAPI 文档的 PHP 属性

    6.2 PHP 文档¶

    • 接口和抽象方法所需（合同文档）
    • @extends / @implements 用于 BaseService 子类的泛型类型
    • @param / @return 仅当类型无法用本机 PHP 表达时
    • 对自记录代码没有评论（命名良好的方法/变量）

    6.3 可见性¶

    • 构造函数注入的服务：protected readonly
    • 内部状态属性：private
    • 挂钩方法：protected（可重写）
    • 公共方法：仅在接口和操作方法上

    7. 代码风格¶

    7.1 PSR-12¶

    标准代码风格。按惯例强制执行。

    7.2 PHPStan 8 级¶

    运行composer phpstan。在 src/ 范围内配置。 8级是最严格的级别 （目前不包括 9 级的 mixed 检查）。

    7.3 Deptrac 架构边界¶

    运行composer deptrac。强制执行： - 核心不能依赖于业务模块 - 模块不得添加对另一个模块的 Entity 或 Repository 的依赖

    deptrac-baseline.yaml 包含经过审查的历史违规行为。新条目需要 明确的架构决策。

    7.4 校长类型规则¶

    运行 composer rector:types:check（CI 试运行）。执行教义 Collection / Repository PHPDoc 泛型。 Broader Rector (composer rector) 是选择加入的并且必须 已审查。

    7.5 命名约定¶

    元素 大会 示例
    课程 帕斯卡案例 CategoryService
    方法 驼峰式 getEnabledCategories()
    属性 驼峰式 $serviceClass
    常数 UPPER_SNAKE UNKNOWN_ERROR
    接口 *Interface 后缀 BaseServiceInterface
    抽象类 Abstract* 或 Base* 前缀 BaseService
    性状 *Trait 后缀或描述性 ListApiViewMixin
    测试 *Test 后缀 CategoryTest

    8. 测试合约¶

    8.1 单元与积分¶

    类别 延伸 目的
    单位 PHPUnit\Framework\TestCase 隔离逻辑（实体、实用程序、计算器）
    内核 IntegrationKernelTestCase 具有启动内核、服务访问、DB
    网页 IntegrationWebTestCase 完整的 HTTP 请求/响应周期
    回归 变化 API合约稳定性

    8.2 测试命名¶

    图案 示例
    {Class}Test CategoryTest.php、OrderServiceTest.php
    {Module}ApiRegressionTest CommonModulesApiRegressionTest.php
    {Module}IntegrationTest WalletApiIntegrationTest.php

    tests/{Module}/ 中的测试反映了 src/{Module}/ 结构。

    8.3 覆盖范围要求¶

    • 最小值：90% 行覆盖率（通过 PHPUnit 在 CI 中强制执行）
    • 测试环境：APP_ENV=test，SQLite数据库
    • 每个测试方法都从一个干净的模式开始（Doctrine模式工具，而不是迁移）
    • 每次测试都会打包交易并回滚

    8.4 测试数据库¶

    测试数据库模式是通过 Doctrine 模式工具创建的，而不是通过迁移创建的。 DatabaseBootstrapTrait 处理架构设置。每个测试都从一个干净的模式开始。

    9.Git 工作流程¶

    9.1 功能分支¶

    分支命名：feature/{description}、fix/{description}、refactor/{description}。

    9.2 常规提交¶

    type(scope): description

feat(identity): add phone verification OTP flow
fix(order): prevent double-submission of payments
refactor(core): extract QueryBuilderFactory from BaseService
docs(manual): add API contracts documentation

    类型：feat、fix、refactor、docs、test、ci、chore。

    9.3 公关模板¶

    在 .github/pull_request_template.md 中可用。必须包括： - 变更摘要 - 进行测试 - 重大变更（如果有） - 检查表（测试通过、静态分析通过、文档更新）

    9.4 审核要求¶

    • CI 必须通过（PHPStan 8 级、Rector 预演、PHPUnit 覆盖率超过 90%）
    • 至少一项对共享核心课程变更的批准审查
    • 迁移文件需要明确审查回滚兼容性

    10. 重大变更¶

    10.1 什么构成重大变更¶

    改变 打破？
    更改钩子方法签名 是 — 主要版本更新
    删除 mixin 方法 是 — 主要版本更新
    更改回复信封格式 是 — 主要版本更新
    删除支持的查询参数 是 — 弃用通知 + 主要版本更新
    更改 BaseServiceInterface 是 — 跨模块影响评估
    更改实体字段类型 是 — 需要迁移
    添加新的 mixin 特征 否 — 仅文档
    使用默认实现添加新的钩子方法 否 — 仅文档
    添加查询参数 否 — 向后兼容
    添加新模块 否 — 遵循模块合同

    10.2 迁移兼容性¶

    • 架构更改需要向后兼容的迁移（旧代码使用新架构读取）
    • 未经明确批准，禁止不可逆迁移（例如，柱掉落）
    • 按模块组织迁移 — 每个模块更改集一个迁移文件

    11. 文件要求¶

    11.1 添加模块时¶

    所需文件 内容
    设计文档(docs/design/{module}.md) 业务流程、API设计、数据模型草图
    捆绑文档 (docs/design/bundles/{module}.md) 模块范围、依赖项、导出接口
    OpenAPI 规范（代码 #[OA\*]） 自动生成于 /api/doc

    11.2 添加服务时¶

    • 关于服务类的 PHPDoc @extends BaseService<EntityClass>
    • 同一命名空间中的服务接口
    • 如果没有自动装配，则在模块的服务配置中注册

    11.3 添加端点时¶

    • #[Route] 属性具有遵循 {scope}-{resource}-{action} 约定的正确 name
    • NelmioApiDoc 的 #[OA\*] 属性
    • #[IsGranted] 用于授权
    • 如果端点需要自定义摘要/描述，则更新 OpenApiEnricherListener::META

    12. 性能指南¶

    12.1 N+1预防¶

    • 使用 @expands 预先加载列表端点中的关系
    • 使用detailProcessor()调用$entity->getItems()->toArray()获取详细视图
    • 避免 @sort （内存中） - 更喜欢 @order （DQL）

    12.2 查询优化¶

    • 使用 @select 只投影需要的字段
    • 使用@filter将过滤推送到数据库
    • 除非必要，否则避免使用 @dql 子查询（使用 @filter 代替）
    • 在存储库中使用 Doctrine 的 indexBy 进行急切加载

    12.3 缓存¶

    • ExpressionService 可以使用 PSR-16 缓存来避免重新解析过滤器
    • cache.app可用于应用程序级缓存
    • JWT黑名单使用缓存（基于TTL）

    13. 安全规则¶

    13.1 安全选择¶

    @select 已列入身份敏感字段的阻止列表（user、profile、password、 roles、email、phone、phoneVerified、refreshToken、sessionKey、rawData）和 对于任何针对 App\Identity\* 实体的查询。

    13.2 特权参数¶

    @dql、@sort、@hints 仅限于 ROLE_ADMIN。 @showDQL 需要 dev 环境。

    13.3 通用过滤器¶

    每个具有列表/详细信息混合的控制器必须覆盖 commonFilter() 来强制执行 所有权和可见性。对于用户范围的端点，始终返回 ['id' => -1] 作为 用户未通过身份验证时的回退。

    13.4 CSRF / XSS¶

    • 所有 API 身份验证均使用 JWT Bearer 令牌（无会话，无 cookie）
    • JSON 响应使用 Content-Type: application/json
    • 没有来自 API 端点的 HTML 渲染
    • 未在框架级别执行输入清理；依赖 Dotrine 参数 防止 SQL 注入的绑定
