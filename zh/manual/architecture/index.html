    架构¶

    1. 服务拓扑¶

    CRUD 平台是一个 多应用程序单一存储库，包含 8 个独立的应用程序 可启动的 Symfony 应用程序以及在运行期间托管它们的根整体应用程序 过渡。每个服务都拥有自己的内核、数据库、迁移、队列、工作线程、 调度程序、容器映像和测试。

    ＃ 服务 命名空间 数据库 状态
    1 巨石（根） App\*（桥梁） app 过渡主机；网关割接后将被删除
    2 常见 App\Common\Main\*、App\Common\Storage\* common 完全提取
    3 身份 App\Identity\Main\*、App\Identity\Wechat\* identity 完全提取
    4 贸易 App\Trade\Trade\*、App\Trade\Promotion\* trade 完全提取
    5 商店 App\Store\* store 完全提取 - 首先提取的服务
    6 库存 App\Inventory\* inventory 提取；生产由安全检查表控制
    7 付款 App\Payment\* payment 完全提取
    8 钱包 App\Wallet\* wallet 完全提取

    共享基础设施¶

    组件 地点 拥有者
    platform-kernel packages/platform-kernel/ 框架（核心）——绝不是商业服务
    integration-contracts packages/integration-contracts/ 共享 — 传输中立的 v1 运营商类别
    legacy-messenger-compat packages/legacy-messenger-compat/ 共享 — 历史上的原生 PHP Messenger 包装器 FQCN
    测试 根 tests/ 根整体——跨模块集成测试

    2. 层架构¶

    每个应用程序都遵循严格的分层架构：

    Request/Response
      ↓
+-----v------------------------------------+
|  HTTP Layer  (Controllers / View Mixins) |  ← Only layer touching Request/Response
+-----+------------------------------------+
      ↓  (Service Interface only)
+-----v------------------------------------+
|  Service Layer                           |  ← All business logic, transactions, validation
+-----+------------------------------------+
      ↓  (Repository only)
+-----v------------------------------------+
|  Repository Layer                        |  ← Data access queries (Doctrine repositories)
+-----+------------------------------------+
      ↓  (Entities only)
+-----v------------------------------------+
|  Entity Layer (Domain Model)             |  ← Persistence and aggregate-local invariants
+-----+------------------------------------+
      ↓  (Doctrine ORM)
+-----v------------------------------------+
|  Infrastructure (ORM, Cache, Serializer) |  ← Framework-provided
+------------------------------------------+

    层依赖规则¶

    规则 来自 至 允许
    R1 控制器 服务 是
    R2 控制器 实体 是（仅键入提示/返回）
    R3 控制器 存储库 否 — 通过服务
    R4 控制器 实体管理器 否 — 通过服务
    R5 服务 存储库 是
    R6 服务 实体 是
    R7 服务 实体管理器 是
    R8 服务 其他服务 是（通过 DI）
    R9 实体 存储库 不
    R10 实体 服务 不
    R11 实体 实体管理器 不

    控制器接收Request/Response对象；服务永远不会。服务自有 通过 BaseServiceInfrastructureTrait::wrapInTransaction() 的事务边界。

    apps/ 与 packages/ 的区别¶

    • apps/：具有自己的内核、数据库的可部署业务服务， 迁移、测试和 Docker 镜像。拥有业务实体和逻辑。
    • packages/：可重用的 PHP 库。包含框架实用程序、合同、 或兼容性垫片。不得包含业务实体或特定于服务的 应用逻辑。

    4. 提取状态¶

    所有 8 个有界上下文都已提取到 apps/。根整体负载 每个通过 Composer 路径包 (crud-platform/{name}-app) 作为过渡主机。

    背景 作曲家包 来源地点 实体去前缀
    商店 crud-platform/store-app apps/store/src/ StoreMembership → Membership、StoreConsumedEvent → InboxMessage、StoreOutboxMessage → OutboxMessage、StoreTradeOrderCancellation → TradeOrderCancellation
    库存 crud-platform/inventory-app apps/inventory/src/ N/A（提取后创建）
    付款 crud-platform/payment-app apps/payment/src/ N/A（提取后创建）
    钱包 crud-platform/wallet-app apps/wallet/src/ 旧版 user_id FK 已删除；仅使用 ownerUuid
    身份 crud-platform/identity-app apps/identity/src/ 不适用
    常见 crud-platform/common-app apps/common/src/ 不适用
    贸易 crud-platform/trade-app apps/trade/src/ N/A（拥有贸易+促销）

    切换状态：所有服务独立启动。巨石仍然是 生产主机。根src/仅保留Bridge/适配器；业务来源是 由apps/完全拥有。

    5. 事件驱动的集成流程¶

    主要集成链是贸易→商店→库存：

    Trade order created (trade.order.created.v1)
  → Store Outbox/Inbox receives event
  → Store creates StoreOrder, validates
  → Store publishes inventory.reservation.requested.v1 (if INVENTORY_ENABLED)
  → Inventory receives, resolves recipes, reserves stock
  → Inventory publishes confirmed or rejected outcome
  → Store receives outcome, accepts or rejects StoreOrder
  → Store publishes store.order.accepted.v1 or store.order.rejected.v1
  → Trade receives, applies workflow transition

    支付→交易使用相同的模式： 

    Payment invoice lifecycle change (payment.invoice.paid.v1, etc.)
  → Payment writes to PaymentOutbox
  → Trade Inbox receives, updates order

    商店→交易（目录同步）： 

    Store directory changes → StoreDirectoryOutboxListener → store.directory.upserted.v1
  → Trade maintains local trade_store_directory projection

    所有链均使用 发件箱/收件箱 模式，并通过 eventId 实现幂等性。 相关 ID 通过链传播以进行分布式跟踪。

    6. 关键设计模式¶

    图案 哪里 详情
    发件箱/收件箱 贸易、商店、库存、付款 在本地事务中写入发件箱的事件；通过调度程序中继；通过 eventId 键控的收件箱幂等消耗
    UUID 身份 贸易、钱包、商店 UUID::v4() 用于外部聚合身份；永远不要跨服务边界公开自动增量 PK
    定价渠道 贸易 PriceCalculatorInterface 实现按优先级排序：BasePriceCalculator(-100) → QuantityCalculator(50) → TotalAggregator(55) → PromotionCalculator(60)
    网关注册表 付款 PaymentGatewayInterface 实现自动标记 payment.gateway，通过 #[AutowireIterator] 收集
    快照 贸易 OrderItem 在创建时捕获 specSnapshot/productSnapshot
    乐观锁定 钱包 Wallet 实体上的 #[ORM\Version] 用于并发访问安全
    软删除 贸易 isDeleted 布尔值 Product、Specification
    通用过滤器 控制器 数组条件或 QueryBuilder 作用域：[] = 管理员、['user' => $user] = 用户范围、['id' => -1] = 阻止所有
    代币轮换 身份 具有重用检测功能的 HMAC-SHA256 刷新令牌
    相关性追踪 整合事件 correlationId通过Trade→Store→Inventory链传播； causationId 是直接父级 eventId
    调整提供商注册表 付款 PaymentAdjustmentProviderInterface 实现自动标记；钱包提供WalletBalanceAdjustmentProvider
    存储驱动程序注册表 存储 MediaStorageInterface 实现标记为 media.storage；可通过多部分 storage 字段进行选择
    促销策略标签 促销 promotion.strategy 自动标记，通过 #[AutowireIterator] 收集（7 种策略）
    余额审计 钱包 GET /app/wallets/balance（用户范围）和 GET /manage/wallets/balance（全局）并进行协调
    表达式查询引擎 核心 @filter、@dql、@order、@select、@groupBy、@sort、@expands、@display、@transform 参数

    7. 跨服务依赖规则¶

    这些规则控制服务在过渡期间如何通信：

    1. 没有跨服务的 Doctrine 关联 — 服务拥有其数据库并 没有 FK、存储库访问或跨越其他服务的事务。
    2. 持久引用使用 UUID — 永远不要引用另一个服务的本地 整数主键。
    3. 仅限标量合约 - 服务边界接受标量命令/查询 并发出标量快照。没有 Doctrine 实体、存储库或 Symfony 请求跨越边界。
    4. 写入发件箱 — 每个状态更改集成事件都被写入 生产者本地事务中的发件箱。
    5. 用于阅读的收件箱 — 消费者使用由 eventId 键控的持久收件箱。
    6. 拥有的队列 - 每个消费者都拥有自己的队列、重试策略、死信 处理、工人和预定作业。
    7. 共享包仅是实用程序 — packages/ 中没有业务实体。

    当前的边界风险（有待在完全独立之前解决）： - 同步InvoiceService→交易订单更新（被发件箱/收件箱取代） - 支付/微信插件合约暴露 Doctrine/Symfony 类型 - 历史队列记录中的旧版本机 PHP Messenger 包装器 FQCN - 耦合支付和钱包的根Bridge/适配器
